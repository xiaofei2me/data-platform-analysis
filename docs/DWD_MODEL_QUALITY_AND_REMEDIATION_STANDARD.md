# DWD 模型质量评估与整改规范

## 1. 目的、适用范围与原则

本规范为业务负责人、数仓架构师、数据工程师和数据治理人员提供一套可执行的 DWD 现状评估、整改决策与验收方法。适用于已上线或拟整改的 DWD 表、其生产任务、上下游模型及下游消费场景。

本规范评估“模型是否满足已确认的业务和技术要求”，不规定所有表都必须采用星型模型、必须包含度量字段、必须使用某种主键或必须拆成特定数量的表。事实表、维度表、事件表、快照表、汇总表等结构均须结合用途和业务合同评估。

遵循以下原则：

1. **业务事件先于 SQL 形态**：先定义业务过程、事件边界和一行的含义，再检查 SQL 如何实现。
2. **证据强于名称**：表名、字段名、候选键、`GROUP BY`、规则命中和 Finding 均是线索，不单独构成业务结论。
3. **区分观察、推断和裁决**：技术上观察到的事实、由规则推导的风险、业务负责人确认的定义分别记录。
4. **状态按维度给出**：粒度、键、JOIN、时间、口径、覆盖等逐项评估；不以单一总分掩盖阻断项。
5. **重复不是天然错误，一对多不是天然放大**：须先确认被建模的事件和预期关系，再判断是否违反要求。
6. **风险与证据置信度分开**：关键指标潜在高影响且证据不足时，应补证据并按风险管理，不得仅因未证实就降级。
7. **可追溯、可复核、可回滚**：所有结论和变更均关联资产身份、SQL/任务版本、验证结果、责任人及生效版本。

本规范是治理和评审方法，不是当前平台已经实现的自动能力说明。现有能力边界见[第 12 节](#12-与当前分析平台的关系)。

## 2. 术语与结论边界

| 术语 | 本规范含义 |
|---|---|
| 业务过程 | 由业务目的、参与对象、起止边界和生命周期定义的一组相关活动，例如下单、履约或退款。过程名称必须由业务责任方确认。 |
| 业务事件 | 过程中的一个可识别发生事实，具有发生时点和业务状态；更正、撤销、重复通知是否另成事件由业务定义。 |
| 粒度（Grain） | 一行所代表的最小业务事实/事件，或经声明的快照、周期、汇总单位。粒度描述行，不等同于实现中的分组字段列表。 |
| 业务键 | 在约定的范围和时态内标识业务实体或事件的字段组合。是否唯一、是否跨来源唯一以及有效期均须明确。 |
| 技术行标识 | 用于追溯物理记录的稳定标识。它可能不同于业务键，也不自动证明业务唯一性。 |
| 合法一对多 | 在明确的事件语义中，一个事实关联多个有效子对象/版本/分摊记录，且目标粒度及度量处理明确的关系。 |
| JOIN 放大 | JOIN 使一条应保持唯一的事实匹配多条右表记录，从而意外重复事实或重复计算度量。它是相对于预期基数和目标粒度的判断，不只看总行数增长。 |
| 机器候选 | Understanding/Review 依据技术信号生成的候选，不是正式业务事实，也不等于已确认缺陷。 |
| 评估结论状态 | 本规范[第 5 节](#5-评估结论状态与人工状态的区别)定义的逐项质量状态。 |

本仓库中 `candidate`、`review_required` 是 Review 机器输出状态；`confirmed` / `rejected` 是人工裁决状态；如 `confirmed_conflict` 等 classification 仍是机器分类。它们都不得替代本规范的质量评估结论。

## 3. 合格 DWD 模型的评估框架

### 3.1 要求级别

| 级别 | 含义 | 评审规则 |
|---|---|---|
| **强制要求（M）** | 适用时必须满足的可审计要求。重点包括用途/责任边界、粒度定义、关键字段语义、转换可追溯、数据风险控制和变更治理。 | 若适用且有证据证明违反，评为 `FAIL`。若定义或证据缺失，不得默认通过，按[状态体系](#5-评估结论状态与人工状态的区别)处理。 |
| **条件性要求（C）** | 只在表的业务语义、消费方式或风险触发时适用。 | 先记录触发条件及不适用理由；适用后按强制要求验证。 |
| **设计建议（R）** | 有助于可理解、可复用、可维护的实践，不是所有表的合格门槛。 | 偏离本身不构成缺陷；只有造成可证明的业务或技术损害时才形成整改问题。 |

| 评估维度 | 级别 | 合格要点 |
|---|---|---|
| 业务对象、过程和模型用途 | M | 表服务的对象/过程、边界、使用者、责任人与权威来源可追溯。正式业务定义已确认；无法从技术命名推定。 |
| 行含义与粒度 | M | 每种记录类型的一行语义清晰、一致，或不同粒度被显式分隔/标识并有明确消费约定。 |
| 业务键与唯一性 | M/C | 对要求唯一的事件/实体定义键、作用域、有效期和去重/更正规则，并按生产代表性数据验证。若业务明确允许重复，须定义重复记录含义。 |
| JOIN 条件、基数与膨胀控制 | M/C | 关系的预期基数、连接条件、有效时态和目标粒度明确；若为多对多/一对多，有明示的展开或聚合策略，并验证度量不会意外重复。 |
| 字段、类型、单位、枚举与转换 | M | 关键字段的语义、来源、类型、单位、时区/精度、枚举、默认值和转换有定义；转换符合已批准口径。非关键/纯技术字段按风险管理。 |
| 时间、分区、增量与历史更正 | M/C | 分区/装载机制可重现且无静默丢数；事件时间、处理时间、时区、迟到数据、回刷范围、更新/更正和保留期均适用于其加载方式。 |
| 事实完整性与数据质量 | M/C | 规定适用的完整性、有效性、唯一性、参照完整性、重复、遗漏、异常监控及处理；阈值由业务风险和数据合同确定。 |
| 金额、数量、状态、取消、退货、退款 | C | 涉及交易/财务/运营指标时，确认正负方向、状态生命周期、净额/毛额、税/币种、取消/冲正/退款、分摊及生效时点；不得假设通用公式。 |
| 模型职责、重复建模、混合粒度 | M/R | 职责、输入输出和消费合同清晰。只有业务等价、范围重叠、逻辑相同且没有合理阶段/来源差异时才判定冗余；混合粒度只有违反明确使用合同才为缺陷。 |
| 来源、上下游和消费场景 | M | 主要来源、转换任务、下游依赖、权威性、关键消费者和影响责任方可追溯；外部/未知端点需单独标记。 |
| 监控、事件处理和变更管理 | M | 按风险设有质量检测、告警/升级、问题责任、回滚或重跑方案、变更记录和下游兼容评估。 |
| 命名、星型结构、字段齐全度、是否含度量 | R/C | 只有组织标准明确适用时才作为条件性要求。纯粹违反偏好不能作为问题。 |

“合格”应表述为“对已定义的适用要求有充分证据支持通过，且不存在未处置的阻断风险”，而不是“无 Finding”或“所有字段均有非空值”。关键业务事实未确认时，评估应明确保留未决状态。

### 3.2 逐维度执行评估表

每个维度都应记录适用性、定义来源、证据引用、验证时间/范围、结论状态、限制和责任人。下表中的技术来源是可查证的证据类型，不表示当前分析平台已经执行了这些验证。

| 维度 | 目标 / 必须证明 | 必须确认的业务事实 | 可取得的技术证据 | 可执行验证与通过条件 | 判定缺陷 / 证据不足 | 整改与验收 / 常见误判 |
|---|---|---|---|---|---|---|
| 对象、过程、用途 | 模型承载对象、过程阶段、输入输出、使用者和 owner 可辨识 | 对象定义、过程起止/包含范围、权威来源、关键消费者、责任人 | 业务目录/访谈、模型说明、DDL注释、任务 SQL、表级血缘、权限/调用清单 | 对每个核心用途列出对象、过程、来源、输出消费者与 owner；业务 owner 签认且引用可复核为 PASS | 只有表名/字段名、没有 owner 或过程未定义时是 `NEEDS_BUSINESS_CONFIRMATION`；无来源/调用证据则 `INSUFFICIENT_EVIDENCE` | 补充业务合同、责任矩阵、来源映射；不得把名称词命中当成已确认过程 |
| 行含义与粒度 | 同一目标记录遵循一种明确粒度或受控的多类型合同 | 一行对应事件/实体/快照/聚合的业务语义和时间边界 | 业务流程、源记录、DDL/字段、INSERT/CTAS、GROUP BY、UNION、过滤、上下游用法 | 按[第 6 节](#6-业务粒度识别流程)完成定义、SQL 追踪和代表性场景验证；记录每种事件是否被分行/聚合 | 已确认单一粒度却发现混写且造成用途/计算冲突，足以 FAIL；候选键多个但无业务合同则待确认 | 按业务事件拆分/加类型和粒度合同，或澄清合理多粒度；`GROUP BY` 和 grain finding 不是粒度证明 |
| 业务键/唯一性 | 唯一性声明与数据真实范围一致，不丢弃合法多记录 | 键组成、scope（租户/来源/BU等）、时态、重发/更正规则 | 业务键合同、源约束、字段映射、受控数据查询、去重 SQL 和写入策略 | 以实际分区/来源/状态/更正场景执行重复和缺键查询；覆盖窗口由 owner 批准；合格标准是合同规定的唯一性/例外率 | 证明违反已批准唯一性且无合法例外可判 FAIL；无数据、键未确认或样本不具代表性时不得判 FAIL/PASS | 修正键/去重范围、保留事件版本或建立稳定技术 ID；重复行不必然是错误，`COUNT(DISTINCT key)` 也不证明所有异常 |
| JOIN 与关联基数 | 每条事实按预期匹配次数关联，不造成非预期计量变化 | 1:1、N:1、1:N 或 N:M 的业务含义；有效期、缺失匹配策略 | SQL JOIN keys/filter、维表快照/有效期、Lineage、源/目标计数、行级关联诊断 | 右侧键在所需 scope 下唯一，或多匹配有明确合同；按事实行检查匹配数、未匹配数、多匹配数，按目标 grain 比较 JOIN 前后；度量对账合格 | 违反约定基数且证明扇出/漏配影响为 FAIL；只看到 LEFT JOIN 或行数增长不能单独判断 | 修复 JOIN 条件、时间版本筛选、维表去重/聚合，或声明合法多值关系；仅凭表级血缘无法判断基数 |
| 字段语义与转换 | 核心字段的类型、精度、单位、枚举、空值和派生公式与合同一致 | 业务定义、单位、币种/税口径、状态映射、默认值含义 | DDL/schema、源字段、CAST/CASE/NVL、字典、SQL、数据样本 | 逐关键字段做“源→转换→目标”映射；检查溢出/精度/枚举覆盖/默认值分布及独立样例；字段 owner 签认 | 与批准定义冲突或确定的截断/单位错配可 FAIL；注释缺失但语义未知应先确认 | 修正映射/类型/精度，保留未知与不适用的区别；字段名相似、类型匹配、`Others` 默认值不能证明语义等价 |
| 时间、分区、增量与历史 | 记录事件时间和可重放范围正确，迟到/更正不会静默丢失或重复 | 时间字段意义、时区、日界线、迟到 SLA、更新/撤销策略、历史保留政策 | 分区 DDL、SQL filters/MAX_PT、调度参数、历史快照、运行记录、数据查询 | 对跨日、迟到、重跑、回刷、历史更正样例验证分区归属、幂等性、覆盖/追加语义及下游影响；符合 SLA/策略 | 已知事件未进入正确区间或重跑造成确定性遗漏/重复可 FAIL；只有 `ds` 列或最大分区用法不能判定业务日期含义 | 修复 watermark/分区键、支持迟到回刷/幂等；物理分区名不等于事件时间，`insert overwrite` 本身也不代表安全或错误 |
| 完整性与质量控制 | 需要的事实被纳入，重复/遗漏/无效值能被发现和处置 | 必需事件范围、可容忍例外、质量 SLA 和告警责任 | 源与目标计数、规则查询、异常工单、监控/调度状态、下游对账 | 按业务切片对账总量与关键子集；验证唯一性/空值/参照/枚举/迟到/异常阈值与告警闭环；阈值有 owner 批准 | 违反批准合同并可复现为 FAIL；没有实际行数据、监控或完整源范围时 `NEEDS_DATA_VALIDATION` / `INSUFFICIENT_EVIDENCE` | 补强规则、监控、重放和隔离流程；SQL parse success、元数据 profile 可用不能代表行级质量通过 |
| 金额、数量、状态与生命周期 | 指标值与状态转换符合已批准业务/财务定义 | 含税/未税、币种/汇率、毛净额、取消/退款/退货/冲正/部分履约、时间归属 | 指标字典、来源明细、表达式、CASE/过滤、Finance-approved totals、受控样本 | 对正向、负向、部分退款、跨期、取消、更正逐场景独立计算并与源/批准报表对账；记录容差和差异解释 | 能证实公式违反已批准口径或少/多计为 FAIL；无已确认指标定义时只能 NEEDS_BUSINESS_CONFIRMATION | 修正公式/事件状态映射并重算影响期间；字段名 `payment`、出现 `return_*` 或汇总相等均不足以证明口径正确 |
| 模型职责与复用 | 每表的责任、转换阶段和消费合同合理；冗余/混粒度须被证实 | 表是否权威、为何并存、BU/来源/生命周期差异、消费方需要的契约 | 多表 schema 对比、完整 SQL 语义、任务/表级血缘、消费者清单、变更记录 | 对比输入范围、过滤、粒度、状态、派生字段、更新时间、使用者与 owner；确认业务等价且逻辑重复、无合理差异后才判重复 | 已证实职责冲突、逻辑重复造成维护/计量问题才 FAIL；字段重叠或相似候选仅是风险信号 | 可能合并、拆分、保留并文档化、弃用接口；合并需兼容/回滚计划；高字段相似度不是冗余证明 |
| 来源、依赖、消费可追溯 | 核心依赖与影响对象可定位，外部/未知依赖有所有者 | 权威源、外部数据解释、消费者/指标关键性 | Snapshot、File/Statement 引用、Lineage、调度平台、Catalog、查询日志 | 对重要输出核实源→任务→表→消费者链；未解析端点逐项归属；对声明的影响范围抽查确认 | 已知源断裂/未经批准依赖并造成影响可 FAIL；没有任务DAG或消费者记录应为证据不足 | 补登记源/映射/owner，恢复/替换异常依赖；SQL 表级 Lineage 不等于调度依赖或消费全量 |
| 监控、事件响应与变更 | 失效能发现、定位、通知、处置；变更影响被控制 | 数据时效/质量 SLA、严重性阈值、值班/升级和业务容忍度 | 监控规则、调度运行、工单/告警、发布记录、回滚方案、下游测试结果 | 对代表性故障演练或历史工单追踪到告警、责任、止损、修复、回归、关闭；变更包含 schema/口径兼容策略 | 强制控制适用但缺失，且违反批准治理要求时 FAIL；没有运行记录时不可声称控制有效 | 增加适用监控、数据合同、回滚/回刷手册；“有调度任务”或“无已知事故”不是有效控制证据 |

### 3.3 状态判定的总闸门

- **PASS** 只可用于适用要求已定义、关键证据覆盖相关范围、验证可复现且结果满足合同的维度。
- **FAIL** 必须指向被违反的已批准业务/技术要求，并附可复现反例或数据/SQL证据。无明确定义时，应先确认要求，不要把偏好伪装成标准。
- 对条件性要求，先判定触发与否。确实不适用且有原因记录，才标 `NOT_APPLICABLE`。
- 多项维度分别判定。一个维度 PASS 不抵消其他维度 FAIL 或待确认。
- 评估状态不能用平均分合并。存在关键维度 `NEEDS_BUSINESS_CONFIRMATION`、`NEEDS_DATA_VALIDATION` 或 `INSUFFICIENT_EVIDENCE` 时，整体应标“未完成评估/有未决项”；存在适用强制维度 FAIL 时，整体标“整改需求已证实”，并同时保留其余未决项。

## 4. 评估证据的使用规则

每条评估结论应包含：`表身份（workspace/project/table）`、`维度及要求ID`、`适用性`、`证据引用`、`观察结果`、`推理过程`、`反例/限制`、`状态`、`评估范围与时间`、`确认人/执行人`。结论至少拆为：

- **Observed（观察事实）**：可直接从元数据、版本化 SQL、执行记录或查询结果复核的事实。
- **Inferred（技术推断）**：由多项证据按明确规则推导出的风险，必须给出规则和适用前提。
- **Business decision（业务确认）**：由业务或数据 owner 签认的语义定义、例外和可接受风险。
- **Data validation result（数据验证）**：在记录的环境、分区、时间窗、样本和 SQL 上得到的实际结果。

优先使用独立且互补的证据：业务定义/数据合同 + 当前 SQL/DDL + 具有代表性的行级结果 + 下游对账。多个机器产物若源自同一个命名信号，不应当作多份独立证明。

证据至少需记录查询/代码版本、Snapshot 或数据时点、过滤条件、分区/来源/状态范围、执行人、结果摘要、异常样本位置与复核方法。敏感数据应只在批准环境按最小必要字段访问，不将行级敏感值写入普通评审文档。

## 5. 评估结论状态与人工状态的区别

### 5.1 本规范的逐维度评估状态

| 状态 | 定义 | 使用条件 |
|---|---|---|
| `PASS` | 适用要求有足够、有效且可复现的证据支持满足。 | 要求已定义、范围充分、结果满足验收标准。 |
| `FAIL` | 可复现证据证明违反已批准且适用的业务或技术要求。 | 记录规范/业务合同条目、违规事实、影响路径和反例。 |
| `NEEDS_BUSINESS_CONFIRMATION` | 技术现象已观察到，但业务语义、允许例外、目标定义或权威性未确认。 | 指定需确认的问题、确认角色与截止条件；不先行判断通过/失败。 |
| `NEEDS_DATA_VALIDATION` | 定义基本明确，但必须用真实/受控数据验证唯一性、基数、对账、覆盖或历史行为。 | 记录所需查询、数据范围、访问批准和结果责任人。 |
| `INSUFFICIENT_EVIDENCE` | 当前输入缺失、不完整、不可追溯或不具代表性，尚无法作出判断。 | 指出缺什么证据、为何无法判定及补齐方式；不得写成“未发现问题”。 |
| `NOT_APPLICABLE` | 该要求对该表/场景确实不适用。 | 记录不适用理由和批准人；不能用于回避未检查事项。 |

业务确认与数据验证可同时未完成，应在评估记录中分别保留（例如业务口径 `NEEDS_BUSINESS_CONFIRMATION`、键唯一性 `NEEDS_DATA_VALIDATION`），不强行压缩成一个状态。

### 5.2 与平台状态的映射边界

| 当前平台字段/状态 | 表达的含义 | 不等于 |
|---|---|---|
| Grain/Fact/Dimension/Process `candidate` | 机器生成候选 | 业务确认、PASS 或 FAIL |
| Finding | 机器识别的结构信号 | 已确认缺陷 |
| Problem `candidate` / `review_required` | 机器聚合候选 / 机器要求重点人工审阅 | 本规范状态 `FAIL` 或业务严重等级 |
| classification（如 `confirmed_conflict`） | 规则内部分类 | 人工 confirmed |
| `human_status=confirmed` / `rejected` | 人工对该候选作出的裁决记录 | 所有质量维度已验证，或问题已实施修复 |
| Coverage `no_finding_under_implemented_rules` | 已有规则未产生关联 Finding/Problem | PASS、充分检查或模型正确 |
| Coverage `insufficient_evidence` | 按 Ledger 定义的证据覆盖不足 | 自动的业务拒绝/确认 |

本规范评估必须单独存档，或通过明确字段映射维护，不得把 `PASS` 写入 Review 的 candidate 状态字段，不得把 Review P0 当作风险评估结论。

## 6. 业务粒度识别流程

必须先从业务过程和业务事件定义粒度，再追踪 SQL 实现。建议逐步执行：

1. **明确业务过程及事件时点**：确认业务事件发生条件、事件源、起止边界、状态变化，以及更正、撤销、重放是否视为新事件。
2. **定义一行的最小业务语义**：用完整句式记录：“在【范围/时间条件】下，一行表示【对象】发生的一次【事件/快照/周期/汇总单元】。”
3. **拆清相邻事件关系**：订单、子订单、商品行、支付、退款、退货、履约可能一对多、多对一或异步发生；确认它们是一个事实行的属性还是独立事实。
4. **提出候选键**：基于事件合同确定候选字段组合及作用域，例如来源系统、BU、版本、业务日期；说明为何能标识事件。候选键不是先从字段名自动挑选。
5. **沿 SQL 检查粒度变化**：逐段追踪 `INSERT` / `CTAS`、JOIN、聚合、去重、过滤、窗口函数、`UNION` / `UNION ALL`、分区覆盖与默认值；列出每一段输入/输出粒度。
6. **用真实数据检验**：在批准的数据范围测试键重复、NULL、覆盖率、同一业务事件映射条数、跨状态/来源/时间/更正样本。验证结果要与业务例外核对。
7. **验证历史和边界场景**：抽查正常、部分取消、退款/退货、迟到、重跑、跨日、来源切换、重复投递、历史更正等实际存在的场景。
8. **业务负责人定版**：记录最终 grain、键合同、例外、责任人、确认日期、生效版本和待办。后续规则/SQL 按版本执行。

### 为什么常见信号不能独立定粒度

- **字段名称**只反映命名意图或历史命名，不证明值的唯一性和事件含义。
- **多个候选键**只表示多个结构组合被提出。它们可能分别唯一、互相包含、覆盖不同来源/事件，也可能全不唯一。
- **重复率**需相对事件合同判断。重复行可能是合法的重复通知、明细展开、版本记录或数据错误；先定义哪一种需要保留/折叠。
- **SQL `GROUP BY`**是实现产生行的分组表达式；它可能过细、过粗，使用的字段也可能是描述属性而非业务键。
- **Review Finding / Problem**表示规则观察和候选聚合，不是行级唯一性检查或业务裁决。

### 订单示例：区分三类问题

仅为说明方法的通用示例，不表示当前样本表已确认采用任何定义。

1. **真实粒度冲突**：业务合同明确目标是一行一个订单商品行；生产 SQL 又将支付尝试或退款事件与商品行 `UNION ALL` 到同表，且没有事件类型/行语义区分，导致同一消费合同中行分别代表不同事件。只有确认合同、查明 SQL 和实际记录后，才能判定混粒度缺陷。
2. **合法一对多**：一个订单有多个子订单，每个子订单含多个商品行；若模型声明一行一个商品行且业务键含订单范围、子订单和行标识，订单对应多行是合法关系，不是重复。
3. **技术 JOIN 放大**：目标合同是一行一个商品行；一条事实行按门店编码 JOIN 到同一有效分区中两条相同门店记录，输出该事实两次。若证据证明重复不是业务有效版本且使销售度量重复，该 JOIN 才构成技术缺陷。合法的一对多子订单关系与错误 JOIN 扇出是不同层次的问题。

## 7. 业务键与 JOIN 实际验证

下列 SQL 是可改写的诊断模板，表名/字段均为占位符，不假设当前 DWD 表具有这些业务键。请在批准的只读/隔离环境执行；先选定目标分区和具有代表性的日期、来源、BU、状态与更正场景，并确认语义和访问权限。不同 SQL 引擎的复合键计数语法可能不同；本规范使用 `GROUP BY` 避免依赖拼接编码。

### 7.1 候选键重复检查

前置：`candidate_key_col_1 ... n` 是业务方确认的候选键；明确其作用域和例外。

```sql
SELECT
    candidate_key_col_1,
    candidate_key_col_2,
    COUNT(*) AS row_count
FROM your_fact_table
WHERE ds >= '<start_partition>'
  AND ds <= '<end_partition>'
GROUP BY candidate_key_col_1, candidate_key_col_2
HAVING COUNT(*) > 1
ORDER BY row_count DESC;
```

检查全部键成员，并分别切分来源/BU/业务状态/事件版本。如果合同允许重复事件，需将重复类别和处理规则一起核对；非空候选键的重复不自动是错误。

### 7.2 NULL / 缺失键检查

```sql
SELECT
    COUNT(*) AS total_rows,
    SUM(CASE
        WHEN candidate_key_col_1 IS NULL
          OR candidate_key_col_2 IS NULL
          OR TRIM(CAST(candidate_key_col_1 AS STRING)) = ''
        THEN 1 ELSE 0
    END) AS missing_key_rows
FROM your_fact_table
WHERE ds >= '<start_partition>'
  AND ds <= '<end_partition>';
```

空字符串检查仅适用于相应类型/引擎，数值、日期和合法 sentinel 应按合同单独定义。确认缺键允许范围、源系统语义和是否可恢复后才能判缺陷。

### 7.3 右表关联键唯一性

对 SCD/版本型维表，必须把有效日期、当前标记或目标分区纳入合同，而不能仅按业务键做全表去重。

```sql
SELECT
    dimension_key,
    COUNT(*) AS matching_rows
FROM your_dimension_table
WHERE snapshot_partition = '<as_of_partition>'
GROUP BY dimension_key
HAVING COUNT(*) > 1;
```

若业务允许同一自然键多版本，需验证 JOIN 条件能选中目标时点唯一版本；重复检查中存在多行不代表时态模型错误。

### 7.4 JOIN 前后记录数及每条事实的匹配数

要求事实侧具有稳定的技术行标识 `fact_row_id`，或使用已经验证的事实粒度键。不要用未验证的候选键假装稳定行 ID。

```sql
WITH dimension_match AS (
    SELECT
        d.dimension_key,
        COUNT(*) AS match_count
    FROM your_dimension_table d
    WHERE d.snapshot_partition = '<as_of_partition>'
    GROUP BY d.dimension_key
),
fact_matches AS (
    SELECT
        f.fact_row_id,
        COALESCE(m.match_count, 0) AS match_count
    FROM your_fact_table f
    LEFT JOIN dimension_match m
      ON f.dimension_key = m.dimension_key
    WHERE f.ds >= '<start_partition>'
      AND f.ds <= '<end_partition>'
)
SELECT
    COUNT(*) AS fact_rows,
    SUM(CASE WHEN match_count = 0 THEN 1 ELSE 0 END) AS unmatched_fact_rows,
    SUM(CASE WHEN match_count = 1 THEN 1 ELSE 0 END) AS one_match_fact_rows,
    SUM(CASE WHEN match_count > 1 THEN 1 ELSE 0 END) AS multi_match_fact_rows,
    SUM(match_count) AS rows_after_left_join
FROM fact_matches;
```

这里的 `rows_after_left_join` 是按右侧记录数计算的预期输出行数，包含零匹配保留的一行。还应将预期匹配数（例如 N:1 应为 0/1，必须匹配则应为 1）与业务合同对照。后续真实 JOIN 验收要检查所有 ON 条件与过滤；CTE 必须复现实际键、有效期与过滤条件。若允许一对多，单独验证目标 grain 是否随之展开或是否先聚合。

### 7.5 JOIN 前后金额、数量和业务记录对账

```sql
WITH before_join AS (
    SELECT
        COUNT(*) AS row_count,
        SUM(quantity) AS quantity_total,
        SUM(amount) AS amount_total
    FROM your_fact_table
    WHERE ds = '<partition>'
),
after_join AS (
    SELECT
        COUNT(*) AS row_count,
        SUM(f.quantity) AS quantity_total,
        SUM(f.amount) AS amount_total
    FROM your_fact_table f
    LEFT JOIN your_dimension_table d
      ON <the_production_join_condition>
    WHERE f.ds = '<partition>'
)
SELECT
    b.row_count AS before_rows,
    a.row_count AS after_rows,
    b.quantity_total AS before_quantity,
    a.quantity_total AS after_quantity,
    b.amount_total AS before_amount,
    a.amount_total AS after_amount
FROM before_join b
CROSS JOIN after_join a;
```

聚合仅用于诊断，不能代替逐事件匹配。维度合法多值可能使记录展开，但事实度量仍须只计一次或按批准比例分摊。若连接条件本身筛除记录、数据含 NULL 或金额有正负冲销，简单总额差异需逐项解释。

### 7.6 来源—目标对账

按与业务合同一致的日期、来源、状态、币种、BU、事件类型等切片，比较源与目标的事件数、唯一业务事件数、数量和金额；逐差异查明加入/排除、延迟、状态转换、舍入、版本与回刷原因。容差、单位、正负号和时点必须预先确认。聚合数完全相等也不证明逐行无误，需抽查事件明细或使用双向差异集。

**禁止结论捷径**：仅因结果表 `COUNT(*)` 增加、`SUM(amount)` 变化、重复查询返回行或 `COUNT(DISTINCT ...)` 相等，不足以独立证明 JOIN 错误/正确。须先明确目标粒度、有效右侧版本、期望匹配数和度量行为，再结合具体匹配记录。

## 8. 评估结论到整改决策

一条评估问题可映射到一个或多个整改任务。只有 `FAIL` 或经风险治理批准的修复行动才进入确定性整改；其他状态先补确认/证据或落实临时控制。

| 整改方式 | 适用条件 | 主要风险 / 影响面 | 必须的验收条件 |
|---|---|---|---|
| 修复 SQL / 任务逻辑 | 有证据证明过滤、聚合、去重、顺序、类型或增量逻辑违反已批准合同 | 历史结果变化、运行时长/成本、调度依赖、临时绕行失效 | 代码评审；新旧逻辑差异解释；代表场景/边界测试；受影响历史期间重算与对账；下游回归及回滚点 |
| 补充数据质量校验与监控 | 合同明确但缺少防线，或缺陷无法仅由一次逻辑修复长期杜绝 | 告警噪声、漏报、任务阻断、阈值误设 | 验证规则在正常/异常样例的召回与误报；告警 owner、SLA、处置/恢复流程明确 |
| 修复业务键或 JOIN | 已证明键或关联条件不满足合同并导致错配/扇出/遗漏 | 表记录数、指标、维度描述和下游消费者同时变化 | 按第 7 节证明匹配基数；修复前后事实行、未匹配/多匹配、度量与样例对账 |
| 调整字段定义或转换 | 单位、类型、枚举、默认值、状态或派生口径经确认不符合定义 | Schema 兼容、历史重解释、消费者静态解析、权限 | 字段映射/数据字典更新；兼容性测试；历史影响分析、必要回刷和业务指标签收 |
| 拆分不同粒度/业务过程模型 | 业务确认同一表合同混合互不兼容的事件/粒度或用途 | 新接口迁移、双写/并行期、历史拆分规则、消费 SQL 改造 | 每个新目标模型均有业务 grain/键/状态合同；源记录完整分配且无意外重复/遗漏；下游逐一迁移验收 |
| 合并模型 | 证实两个模型语义等价、重复加工且差异可解释为非业务差异，owner 同意弃用/收敛 | 失去 BU/来源/时效特例、下游耦合、历史差异 | 逐字段/逐事件语义等价证明；消费者清单签收；过渡/兼容/回滚策略；历史数据对账 |
| 重建模型 | 现有逻辑/契约不可安全渐进修复，且新模型目标定义已批准 | 最大的数据迁移、历史重算、消费者和运行成本风险 | 设计评审、来源覆盖、历史回刷计划、对账门槛、双轨验证、切换/回滚与 owner 批准 |
| 保留模型并补文档、监控或血缘 | 设计经业务确认合理，主要问题是定义、可观测性或可追溯缺失 | 新文档与实际漂移；监控维护成本 | 文档 owner/版本、生效时间；质量规则和告警演练；上下游/消费登记核对 |
| 暂不整改、先补业务事实或技术证据 | NEEDS_* 或 INSUFFICIENT_EVIDENCE，尚无条件支持结构变更 | 风险继续存在；延迟可能影响指标或项目 | 列出负责人、数据/业务输入、临时控制、截止时间和升级条件；到期复评，不记作 PASS |

方案评审需记录备选方案、影响表/任务/指标、受影响期间、迁移顺序、兼容期、回滚、成本/性能、访问/安全影响及批准人。禁止仅根据 Finding 类型自动推出合并、拆分或重建决策。

## 9. 整改优先级：业务风险与证据置信度分开

### 9.1 风险等级

| 建议风险等级 | 判定原则 |
|---|---|
| **P0 — 紧急控制** | 已发生或高度可信地可能导致核心财务/经营指标重大错报、广泛下游错误、合规/客户影响或不可恢复历史丢失；需立即止损、隔离或高层升级。依据已批准风险容忍度，不由机器标签产生。 |
| **P1 — 高优先级** | 可能显著影响关键过程、重要数据产品或多个关键消费者；存在可观测风险，需要短期内确认并制定控制/修复。 |
| **P2 — 常规计划** | 影响范围有限或存在有效控制/可恢复手段；安排在明确迭代内处置。 |
| **P3 — 改善事项** | 文档、可维护性、低影响覆盖或非关键建议；无已证实业务错误，按治理容量排期。 |

等级要看实际/潜在损害、影响对象、数据传播、持续时长、可恢复性和控制措施。未知但潜在涉及关键指标/财务影响时，应暂按较高风险管理并迅速补证据，不得因“不确定”直接降到 P2/P3。

### 9.2 证据置信程度（单独记录）

- **高**：证据直接且相互独立；生产 SQL / 数据范围清晰；可复现；业务合同已确认；替代解释已核查。
- **中**：关键技术链已追踪，但存在有限范围/抽样限制，或尚有未关闭的合理解释。
- **低**：只依赖命名、相似度、规则候选、局部样本、缺失产物或未确认业务定义。

置信度描述“当前结论依据多强”，不代表损失严重度。高风险 + 低置信度的正确处置是优先补证据/止损，而非自动降风险；低风险 + 高置信度可计划处理。

### 9.3 排序信息

至少记录：实际/潜在业务影响、关键指标/消费者、重复计量/遗漏/历史错数可能、影响 workspace/表/任务/下游传播、持续时间、现有控制与恢复能力、证据置信程度、业务 owner、下一动作和期限。相同问题族的重复 machine candidates 应去重或关联管理，不按 candidate 条数叠加风险。

## 10. 整改验收闭环

### 10.1 特殊变更必须追加的验收

- **粒度或业务键变更**：新旧粒度映射规则、目标唯一性查询、旧记录重组/多对多处理、按时间/来源/状态/更正切片对账；不得以总行数相等代替。
- **JOIN 条件或维表策略变更**：逐条事实匹配数、未匹配/多匹配率、维度版本有效期、JOIN 前后事实数和核心度量对账；核实合法一对多。
- **金额/数量/状态口径变更**：业务/财务批准定义、正负方向/税/币种/舍入/取消/退款/退货案例、按历史期间重算影响及与批准口径报表对账。
- **分区/增量/历史逻辑变更**：回刷窗口、迟到/更正样例、幂等重跑、分区遗漏/重复及下游延迟；验证覆盖策略和回滚恢复。
- **拆分/合并/重建**：来源事件覆盖完整、下游消费者迁移清单和签收、旧接口弃用时点、并行期差异、权限/成本影响及可逆切换方案。

关闭标准不等于“代码已上线”。若历史数据未回刷、下游未回归、业务未签收或临时控制未到位，状态应保持开放或部分完成。

该状态是本规范的**示范评估状态**，不是平台字段。没有任何维度可因“解析成功”或“无技术错误”自动标成质量 PASS，也没有当前数据证据足以作 `FAIL` 的确定结论。

#### 必须完成的确认与验证

1. 由电商业务负责人确认一行代表订单、子订单、商品明细、支付/交易事件还是其他记录；明确事件发生时点及跨来源对应关系。
2. 与业务/主数据 owner 确认候选键的组成和作用域，以及同一订单商品允许多次支付、拆分、退货、版本更正或重复通知的规则。
3. 由财务/指标 owner 确认 `quantity`、`payment_actual`、`total_price_tax` 等指标公式、币种/税、退货退款及零值过滤口径。
4. 由数据平台/电商 owner 确认 `ds` 的业务含义、最大分区策略、迟到数据、重跑、回刷和历史更正方式。
5. 在获批数据范围按第 7 节验证候选键唯一性/缺失率；按生产精确条件验证 customer/store/mapping JOIN 的每条事实匹配数和 JOIN 前后度量变化。
6. 选取代表性正常、取消、退款/退货、更正、迟到和不同来源样例，逐步对账源输入、临时表、目标表及重要下游消费。记录实际 SQL、分区、执行时点、差异和审批人。
7. 对 `problem_0877`、`0992`、`0993`、`1000`、`1003` 的重叠表组逐一确认职责和 SQL 差异；拆解 `problem_1159` / `1169` 的宽范围，不把整组表当成一个可实施整改项。

可能路径包括：若证实 JOIN 扇出，修正右表时态/唯一性或关联条件；若口径/键定义有误，按批准合同修复并重算历史；若确实存在互不兼容事件粒度，评审拆分或显式类型设计；若多表是合法处理阶段，则保留并补全职责/消费者/监控文档；证据不足时暂缓结构修改并设责任人和截止日期。

**当前结论**：这是一个证据可导航、适合优先评审的 DWD 候选表，但不是已确认缺陷。当前没有行级结果证明候选键不唯一、JOIN 放大、金额计算错误或实际粒度冲突。进入模型改造设计前，至少要有经业务签认的用途/事件/grain/键/指标/时间合同、可复核的 JOIN 和行级数据验证、上下游影响与消费者清单、评审批准的方案/回刷/回归门槛。此时只能开展评审和补证，不能据候选 Problem 批准改造。

## 13. 可选的未来自动化建议（非本次实现）

未来若扩展平台，可考虑引入版本化质量合同/业务事实引用、运行 Snapshot 与代码 provenance、对 Review 候选提供 SQL Statement/字段血缘导航、授权的安全行级质量查询、join cardinality diagnostics、来源目标自动对账结果和问题/整改生命周期。它们均不属于当前已实现能力，不应在没有数据访问审批、业务 owner 和清晰输入契约时自动执行或写回业务规则。

本规范不修改现有规则、候选、Snapshot 或配置；业务确认事实应先进入受控人工评审记录，是否结构化供 Understanding 消费须另行评审并版本管理。
